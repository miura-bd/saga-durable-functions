# 本番の処理にする前のメモ

builders.flash 記事「Lambda Durable Functions で、途中で落ちても続く SAGA を書く」の補足です。
記事のサンプルを、本番の補償処理に寄せるときの考え方をまとめています。
数値は記事執筆時点（2026 年 10 月）の Lambda Durable Functions の仕様にもとづきます。

## Durable Functions の再開で足りるかどうかの見分け方

自分の処理に当てはめるための早見表です。
Durable Functions の再開で足りるのは、落ちてもやり直せる処理です。
再開だけでは守れない処理には、冪等キーや台帳といった別の手当てが必要になります。

| 処理の性質 | Durable Functions の再開で足りるか | 必要な手当て |
|---|---|---|
| 読み取り・計算だけ（副作用なし） | 足りる | 特になし |
| 冪等な書き込み（同じキーに上書き。例：視聴ページを閉じる、リソースを解放する） | 足りる | 冪等なキー設計（PutItem の上書きなど） |
| 外部へ 1 回だけ送る（例：配信先への中止連絡、メール、課金） | 再開だけでは危険 | 冪等キー（副作用のあと・step の記録前に落ちたときの再実行を受け止める） |
| 結果不明のまま終わる外部呼び出し（タイムアウト・5xx） | 再開だけでは危険 | 台帳＋結果照会／Webhook 待ち（勝手に再送しない） |

判断の軸は、「落ちた後にその処理をもう一度実行して、副作用が増えないか」です。
増えないなら Durable Functions の再開に任せられます。
増えるなら、増えないように冪等キーか台帳で受けるようにします。

## 本番の補償処理にする前に（設計の考え方）

サンプルはオーケストレーションの書き方を見せるためのもので、モックは DynamoDB 上の状態を更新するだけです。
実際の外部サービスを相手にするなら、次はサンプルの外で設計が必要になります。

- 冪等キーを先に押さえます。サンプルの中止連絡は「キーを読む → なければ送る → キーを書く」の順ですが、本番では条件付き書き込み（`attribute_not_exists`）で先にキーを押さえるか、相手の API の冪等キーに任せます。呼び出しごとに一意な ID を求める API なら、UUID は step の中で作り、step の結果として保存させます（step の外で作るとリプレイのたびに変わります）。
- 冪等キーは台帳に置きます。タイムアウトや 5xx など結果が分からないときは送り直さず、結果照会や Webhook 待ちへ遷移させます。
- 完了通知（Webhook）は重複・遅延・順不同で届きます。署名検証と受信イベントの冪等化、台帳への状態遷移に分けて、後着イベントを無条件に採用しないようにします。
- レート制御も要ります。相手のサービスごとに、429（レート制限）／`Retry-After` に準拠したバックオフを設けます。
- 同じ公演日の実行を二重に起動しないよう、実行名（execution name）を `eventId` から決めます。同じ名前と同じ入力で起動し直すと、新しい実行は始まらず、既存の実行の情報が返ります。
- 当日の実行の外で中止を扱う入り口（前日以前に中止が決まった場合など）は、サンプルに含めていません。その場合は、何を打ち消すかを積んだ配列ではなく、その時点の状態（リソースを確保済みか、視聴ページを公開済みか、配信先へ連絡済みか）から決めます。
- 「ワークフローの成功」と「業務の完了」は別物として扱い、補償が人手に渡った件（補償の途中で失敗したときなど）は、キュー・SLA・証跡まで設計しておきます。

### 落ちても安全にするためのチェックリスト

- [ ] 外へ 1 回だけ送りたい副作用には冪等キーがあり、再実行で増えない
- [ ] 冪等の判定材料を外部の台帳（DynamoDB など）に置き、プロセス内メモリに依存しない
- [ ] 結果不明（タイムアウト・5xx）のときは送り直さず、結果照会／Webhook 待ちへ分岐する
- [ ] 補償の途中で失敗したときに、補償を最初からやり直さない（`compensable` のような目印）
- [ ] 補償スタックの配列はハンドラの中で作る（ハンドラの外だと、使い回された実行環境に前の中身が残る）
- [ ] step の外では現在時刻や乱数を使わない（使うなら step の中で作って保存させる）
- [ ] Durable Functions の関数はバージョンかエイリアスに固定して呼ぶ（`$LATEST` の決定論崩れを避ける）
- [ ] 実行タイムアウトが 15 分を超える Durable Functions の関数は、非同期起動＋結果取得で呼ぶ
- [ ] 1 回の実行で使う operation の数や、チェックポイントに保存するデータの量を見積もり、公式のクォータ（[Lambda のクォータ](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html)）に収まるか確かめる
